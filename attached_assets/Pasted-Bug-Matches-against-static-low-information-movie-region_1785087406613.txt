Bug: Matches against static/low-information movie regions (transitions, blank frames, static shots) produce false-positive segments
Root cause found: examining matchSequence detail of the false-positive segments (the ones with speedRatio ≈ 0.1), the movieTime values are nearly frozen — oscillating within a very narrow window (e.g. 1 second of movie time) while shortTime progresses normally across the clip. This happens because that movie region has low visual information/detail (e.g. a transition, fade, static shot, or blank/dark frame), making its frames abnormally similar to each other — and by extension, spuriously similar to unrelated short-clip frames that also happen to be low-detail (transitions, blur, dark moments) in the short clip.
Task:
In server/matching-engine.ts, add a frame-detail/information-content check before accepting a frame-pair match: compute a simple "detail score" for both the short-clip frame and the matched movie frame (e.g. using existing signals like detailSim already present in bestFrameDetail, or a variance/entropy measure on the grayscale pixel data — reuse whatever's cheapest given what's already computed in the pipeline).
If either frame in a matched pair has very low detail (below a configurable threshold — e.g. mostly flat color, low edge variance, indicating a transition/fade/blank frame), treat that individual frame-match as low-confidence or exclude it from contributing to segment formation, since low-detail frames are inherently unreliable for matching (too many false positives possible).
Add this as a per-frame gate that runs during the matching pass (or as a post-hoc segment validation, whichever fits the existing pipeline structure better) — log when a frame-pair is skipped/down-weighted for this reason, e.g. [Matcher] Low-detail skip: movie frame at 405.68s (detailScore=X) — insufficient information content for reliable match.
This should naturally reduce or eliminate the speedRatio ≈ 0.1 and sequence-jump false positives already reported, since those all trace back to matching against these low-detail movie regions — implement this as a root-cause fix that likely also resolves the two previously reported bugs. Please cross-check: after implementing this, re-run the same test case and confirm the previously-flagged bad segments (the ones with speedRatio≈0.1 and sequence jumps) are now gone or greatly reduced.
Still keep the speedRatio and sequence-consistency checks as a secondary safety net (defense in depth) in case some low-detail false positives slip through this primary fix.
Strict constraints:
Be careful not to reject genuinely valid matches that happen to be simple/low-detail but real (e.g. a solid-color logo card that legitimately appears in both movie and short clip) — the threshold should target clearly-degenerate frames (near-blank, heavy blur, solid color) not just "simple" scenes. If unsure, err toward flagging for review/lower-confidence rather than hard rejection.
Report before/after segment counts and specifically confirm whether this fix resolves the previously-reported speedRatio/sequence-jump bugs (they may turn out to be the same underlying issue, in which case only one fix — this one — may be needed).
Test with existing test files to confirm no regression on legitimate low-but-real-detail matches.
