Feature: Add SIFT/ORB keypoint-based geometric matching as an additional signal
Our current matching (src/shared/fingerprint.ts, server/matching-engine.ts) uses whole-frame perceptual hashes (aHash/dHash/pHash) and CLIP embeddings — both look at overall frame pattern/content, but neither explicitly tracks distinct geometric points (corners, edges, unique textures) within a frame. Adding keypoint-based matching should help in cases of heavy cropping, perspective/angle changes, or partial occlusion, where the overall frame pattern shifts but specific distinctive objects/points remain geometrically consistent between the short clip and the movie.
Implementation:
Use a well-established, license-free keypoint detector — ORB (Oriented FAST and Rotated BRIEF) is strongly preferred over SIFT for this use case, since ORB is patent-free, much faster, and works well in Node.js via OpenCV bindings (opencv4nodejs or a WASM-based OpenCV build), whereas SIFT is heavier and licensing has historically been a concern (now expired, but ORB remains the better performance/cost tradeoff for a per-frame pipeline at scale).
Add a new file server/keypoint-signal.ts that: loads/initializes the ORB detector once at startup, and exposes a function getKeypoints(imageData): { keypoints: number[][], descriptors: Uint8Array } that detects keypoints and computes their descriptors for a single frame.
Do NOT run this on every frame in the main pipeline pass — it's computationally heavier than hash computation. Instead, run it only as a second-pass confirming/rescuing step, using the same borderline-detection pattern already established for the face/hand/object signals in server/matching-engine.ts (the BORDERLINE_MIN/BORDERLINE_MAX filtering around line 2334).
For borderline segments, run getKeypoints on the corresponding short-clip and movie frames, then match descriptors between them (e.g. using a brute-force Hamming-distance matcher for ORB's binary descriptors, or a ratio test to filter good matches) and count the number of strong keypoint matches (a proxy for geometric consistency between the two frames).
Combine this into a keypointSim score — e.g. based on the number/ratio of strong matched keypoints relative to total keypoints detected — and use it the same way as the other borderline-rescue signals: if hash/CLIP similarity is borderline AND keypointSim is high (many consistent geometric matches), boost confidence to confirm the match.
Log clearly when a match is rescued or confirmed by this signal, e.g. [KeypointSignal] Borderline match at frame X confirmed by ORB keypoint matching (X strong matches out of Y detected, keypointSim=Z%).
Strict constraints:
This is an additive confirming signal only — same rule as the existing face/hand/object signals: never overrides a clear hash/CLIP-based non-match into a match, never downgrades a clear match, only resolves genuinely ambiguous/borderline cases.
Must not slow down the main first-pass pipeline — keypoint detection only runs within the same conditional second-pass step as the other borderline signals, on the same small subset of frames.
Confirm the chosen library/approach is fully self-hosted with zero recurring cost and no external API dependency — same requirement as our existing MediaPipe/CLIP integrations.
Report the Docker image size increase (if any native dependencies are added) and the added processing time for the borderline-case second pass only.
Test with existing test files to confirm no regressions, and if possible test with a heavily-cropped or angle-shifted clip to validate this signal actually helps in that specific scenario.
