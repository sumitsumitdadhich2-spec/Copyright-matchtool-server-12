Prompt 2 — Dynamic Time Warping (DTW) for Segment Alignment
Feature: Add DTW-based sequence alignment to improve segment merging, especially for speed-varying clips
Our current segment-formation logic (server/matching-engine.ts) uses a scene-chunk detection + multi-pass merge approach (Pass 1/2/3 with different similarity thresholds, followed by segment merging and context validation). This works well but treats frame-to-frame alignment somewhat rigidly. Dynamic Time Warping (DTW) is a more mathematically robust alignment technique specifically designed for aligning two time sequences that may vary in speed/timing — it finds the optimal alignment path between the short-clip frame sequence and the movie frame sequence even when their relative speed changes partway through (e.g. part of a clip is normal speed, another part is slowed down).
Implementation:
Add a new function in server/matching-engine.ts (or a new file server/dtw-align.ts if cleaner) that implements DTW alignment between the short-clip frame sequence and a candidate movie region's frame sequence, using the existing per-frame similarity scores (the same aHash/dHash/pHash/CLIP combined similarity already computed) as the local cost/distance metric at each (short-frame, movie-frame) pair.
The DTW algorithm should compute the lowest-cost alignment path through the similarity matrix, which naturally handles cases where the short clip's speed relative to the movie changes over the course of a segment (which is likely related to the speedRatio anomalies already reported — some of those may be genuine speed-varying matches that the current rigid frame-stepping approach handles poorly, as opposed to true false positives; this DTW pass should help distinguish the two).
Use this as an alternative/additional alignment pass for segments that are borderline or where the existing pass logic produces a poor or inconsistent speedRatio — rather than replacing the existing scene-chunk + merge logic entirely, run DTW as a refinement/re-alignment step on candidate regions that the current approach struggles with (e.g. segments flagged as borderline by confidence, or ones with implausible speedRatio from the previous bug reports).
If DTW produces a smoother, more consistent alignment (i.e. a lower total path cost with a more plausible speed profile) than the existing rigid approach for a given segment, use the DTW-refined boundaries/alignment instead. If DTW doesn't improve things, keep the existing result.
Log clearly when DTW alignment is used and changes the outcome, e.g. [DTW] Re-aligned segment [short 7.00-9.08s] — original speedRatio=0.10 (implausible), DTW-refined alignment found speedRatio=0.85 (plausible) — using DTW result. or [DTW] Segment [short 7.00-9.08s] — DTW did not find a better alignment, keeping original result.
Since DTW's computational cost grows with sequence length (it's O(n×m) for two sequences of length n and m), do NOT run it on the full short-clip-vs-full-movie comparison — only apply it to the already-narrowed candidate regions/segments identified by the existing fast hash-based scanning, similar to how the CLIP and other signals are scoped to avoid full-video cost.
