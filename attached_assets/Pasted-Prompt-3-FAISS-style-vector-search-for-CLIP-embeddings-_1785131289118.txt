Prompt 3 — FAISS-style vector search for CLIP embeddings (replace/augment the sequential walk for candidate-finding)
Feature: Add approximate-nearest-neighbor vector search over CLIP embeddings to find candidate movie regions, as an alternative to the sequential frame-drift walk
Our current matching approach (walkOneDir in server/matching-engine.ts) finds a seed match, then walks frame-by-frame in both directions with a configurable frame-drift tolerance (default ±3). This works well for most cases but can still struggle when speed variation or frame drops are large enough to exceed the drift window, since it's fundamentally a local, sequential search from a starting point rather than a global search.
Task:
Since CLIP embeddings are already computed and stored per-frame when ENABLE_CLIP_MATCHING=true (server/embedding.ts, .embeddings.bin files), add a vector index over the movie's embeddings using a lightweight, self-hosted library — use hnswlib-node (HNSW is functionally similar to FAISS for approximate nearest-neighbor search and has a well-maintained pure Node.js binding, avoiding the need for FAISS's heavier Python/C++ build toolchain in our Node-based pipeline) rather than FAISS directly.
Add a new file server/vector-index.ts that builds an HNSW index from a movie's embeddings once (cached alongside the existing fingerprint files, e.g. *_result.json.hnsw.bin), and exposes a function findNearestMovieFrames(shortClipEmbedding, k): { movieFrameIndex: number, distance: number }[] that returns the top-k most similar movie frames for a given short-clip frame's embedding.
Use this as an additional candidate-finding method alongside (not replacing) the existing seed-search: for each short-clip scene chunk, in addition to the current seed-finding approach, also query the HNSW index for the chunk's frames to surface candidate movie regions that the sequential/local approach might miss entirely (e.g. because the true match is far outside the frame-drift window due to heavy speed variation or a large frame-count mismatch).
Any additional candidate regions found this way should be run through the exact same downstream pipeline as regular candidates — scene-chunk matching (Pass 1/2/3), then all the same post-match filters (context validation, speedRatio filtering, sequence-consistency filtering) — so they're held to the identical quality bar, not given special treatment.
Log when the vector-search approach surfaces a candidate the sequential walk didn't find, e.g. [VectorIndex] HNSW found alternate candidate movie region at Xs for short-clip chunk [Y-Zs] (not reached by sequential walk) — passed to standard matching pipeline for verification.
Strict constraints:
This only applies when ENABLE_CLIP_MATCHING=true (since it depends on CLIP embeddings existing) — when CLIP is disabled, matching continues exactly as it does now with no vector search step.
This is an additional candidate-discovery method, not a replacement for the existing seed-search/walk — both should run, and results should be merged before the standard filtering pipeline, not one replacing the other.
Report the time cost of building the HNSW index per movie (this is a one-time cost per movie upload, should be reported separately from per-match query cost) and the query cost per short-clip chunk.
Report whether this surfaces any genuinely new true-positive matches on our existing test cases that the sequential approach missed, and confirm no regression in cases that already worked.
Confirm hnswlib-node has no runtime external dependency or cost — fully self-hosted, matching our existing constraints for all other signals.
