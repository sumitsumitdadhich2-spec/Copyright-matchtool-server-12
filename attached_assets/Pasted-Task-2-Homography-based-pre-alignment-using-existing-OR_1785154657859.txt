Task 2 — Homography-based pre-alignment using existing ORB keypoints
Currently, server/keypoint-signal.ts's ORB-lite keypoints are used only to compute a keypointSim score for borderline segments (§6 of the architecture doc) — they are not used to actually transform/align frames before hashing.
Add a new capability: when a short-clip frame is being compared against a candidate movie frame (or crop-variant of one) and the frame is a borderline case OR the user has cropped/rotated/zoomed it in a way that doesn't cleanly match one of the 13 preset crop/zoom variants (e.g. the winning crop variant's keypointSim is only moderately good, suggesting a near-miss alignment rather than a clean hash match) — compute a homography transform from the matched ORB keypoint correspondences between the two frames, and warp the short-clip frame to align with the movie frame's perspective/scale before computing a refined hash comparison on the aligned result.
This refined, post-alignment hash score should be used as an additional signal (e.g. alignedHashSim) feeding into the existing borderline-enhancement pass (the same 55-75% confidence range pipeline as the other rescue signals) — not as a blanket replacement for the existing 13-crop-variant matching, which should remain the fast first-pass default for clean, standard crops.
Log when homography alignment meaningfully changes the outcome, e.g. [Homography] Aligned short-clip frame at Xs to movie frame at Ys (rotation=Z°, scale=W) — refined hash similarity improved from A% to B%.
Only run this for segments that are already in the borderline pass — this is computationally heavier than the standard crop-variant hashing and must not run on every frame of the main pipeline.
Strict constraints:
This is a pre-processing/alignment improvement that can genuinely raise a score by correcting a real geometric mismatch — it is not the same as artificially curving a score, since it's recomputing the hash on a properly-aligned image rather than modifying the score of a misaligned one. Be careful not to blur this distinction: the log output and any internal documentation should make clear this is "corrected the comparison," not "boosted the result."
Must not slow down the main per-frame pipeline — homography + realignment only runs within the existing borderline second-pass scope.
Test with existing test files to confirm no regression, and if possible test specifically with a rotated/off-center-zoomed clip (not matching any of the 13 preset crop variants cleanly) to confirm this signal helps in exactly that scenario.
